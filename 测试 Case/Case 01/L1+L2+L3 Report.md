# After Sending 交易推进页 · 测试结果（L1+L2+L3）

> 本文件是一次完整的「设计自驱类需求」走查记录，覆盖：原则召回 → 设计目标 → 设计说明 → 设计反思。

## 0. 需求背景与理解（上下文）

### 0.1 需求背景

当前页面为国际汇款产品的「After Sending」——选择汇款到微信之后的状态页，用于展示汇款后的交易状态并引导用户完成后续收款。目前页面由交易时间线（Timeline）、交易状态、交易子状态、收款通知（ShareLink / Recipient Notification）组成，整体偏「状态展示」。

本次目标：把该页从**状态展示页**升级为**交易推进页**——在展示状态的同时，更主动地引导用户完成收款、推动交易尽快完成。

**两类核心场景：**
- **自汇自收（Self → Self）**：用户希望尽快前往微信完成收款。
- **自汇他收（Self → Others）**：用户希望尽快通知收款人，并推动其完成收款。

**边界与约束：** 原型探索阶段，不受现有结构和视觉布局限制；不新增后台能力；可动的杠杆是信息架构、内容层级、模块顺序、时间线呈现形式、CTA、文案、交互。

**通知能力现状：** ShareLink 现有「前往微信」（H5 中转 → 微信 / 短信 / 又想 / copy 链接）；若都不可用，可兜底贴一个「收款攻略」蓝链。

**触发点：** 通知收款人的 CTA 挂在时间线第 4 个节点「Waiting for LI SI to get setup on Weixin」（当前活跃节点）。前 3 节点（set up / received USD / verified）已完成，末节点「We pay out your CNY」为未来态。

**数据现状：** 流失 / 客诉集中在哪一步，暂无数据支持（按假设的高风险断点排优先级推进）。

### 0.2 确认后的需求理解（体验视角）

用户刚把钱汇出，站在这页时心里只有一件事：**"钱我付了，现在到底该我干嘛？这事儿算成了没？"** 当前页面回答的是"我们（平台）这边发生了什么"，没回答用户此刻真正在问的"**接下来轮到我做什么、我做完会怎样**"。所以升级的本质不是加按钮，而是把叙述主语从"我们"切到"你现在这一步"。

**关键定性：这页自始至终是「汇款人视角」，两类场景都只回答"轮到你（汇款人）做什么"，不越界去讲收款人那边要干嘛。**

| | 自汇自收 | 自汇他收 |
|---|---|---|
| 这页要推汇款人做的**唯一动作** | 去微信，自己收 | 去通知收款人 |
| 现在最该讲清的 | 去微信会到哪、怎么收、大概多久 | 通知谁、用什么方式一键送达、为什么现在就得通知 |
| 不该在这页展开的 | —— | 收款人拿到链接后的操作步骤（交给触达落地页承接） |

**两个被确认的核心痛点（其余搁置）：**
- **痛点 ②｜跳转前的未知**：用户不知道"点了之后会去微信的哪个页面、到了要做什么"，跳转是一次跨平台盲跳。
- **痛点 ③｜自收被"分享给收款人"误导**：自己就是收款人的用户，被一句 "Share to recipient" 引导去"分享给别人"，产生动作误解与中断；同时他收用户也没被清楚地推成"现在就去通知"。

**页面职责定性：** 这页要从「结果·状态反馈」，长出「前往·通知触达 + 前置指引」的职责。时间线退居为"可信度背书 + 资金可追溯"；真正的主角是"现在轮到你，这样做"的行动区。

## 1. 原则召回

> 从 L1 / L2 / L3 三层召回，每条召回原因拆成 **① 为什么本需求要调它** 和 **② 它指导解决什么问题·对本设计的自驱价值**。

### 1.1 L1 · 通用原则

| 层级 | 设计原则 | 召回原因 |
|---|---|---|
| L1 | **L1-01 先确认用户为什么需要这个设计** | ① 本次是"状态展示→交易推进"的升级，若不先锚定用户在这页的真实动机（"钱付了，轮到我干嘛"），升级会沦为堆 CTA；② 用 JTBD 校准页面叙述主语，从"平台发生了什么"切到"你现在这一步"，为整套方案定靶。 |
| L1 | **L1-02 不能为达成目标牺牲用户理解与信任** | ① "推进交易"天然有靠催促、放大焦虑、遮挡信息拉动作的诱惑，跨境资金场景伤信任代价极高；② 作为护栏，用"让用户更确定"而非"制造紧迫"的方式推进，守住长期信任。 |
| L1 | **L1-03 先让用户完成核心任务，再补充更多内容** | ① 已确认"这页只服务汇款人下一步、收款人侧外推"，取舍需要背书；② 先保住"轮到你做什么"的必要范围，把非核心内容延后或外移，避免失焦。 |
| L1 | **L1-05 让用户知道自己在哪，下一步去哪（P0）** | ① 痛点②正是"不知道去微信之后到哪、做什么"的盲跳；② 让当前位置、下一步动作、跳转去向持续可见，降低绕路与放弃。 |
| L1 | **L1-06 复杂信息要按理解节奏逐步展开（P0）** | ① 时间线 5 节点 + 跳转预期 + 两类场景信息一次压上会过载；② 按用户当下决策节奏分层，先"轮到你做什么"，细节与历史再展开。 |
| L1 | **L1-07 界面要让用户一眼认出可操作项（P0）** | ① 主 CTA 埋在时间线第 4 节点、与已完成节点同权，认不出；② 强化主操作识别线索，让"现在该点这里"一眼可辨。 |
| L1 | **L1-08 让用户清楚理解当前动作和结果（P0）** | ① 痛点③——自收用户被 "Share to recipient" 误导；② 用贴近真实理解的动作文案，让两类用户都清楚"我在做什么、会得到什么"。 |
| L1 | **L1-13 视觉要先帮助用户分清主次** | ① 需要把"下一步动作"从时间线里抽出、升为主角；② 建立清晰视觉优先级（行动区 > 当前状态 > 历史时间线）。 |
| L1 | **L1-16 关键状态不能只靠单一线索表达** | ① "进行中"节点仅靠一个蓝色圆点区分，颜色单线索易漏读；② 用文案 / 图形 / 位置多线索共同表达当前所处步骤。 |

### 1.2 L2 · 跨境原则

| 层级 | 设计原则 | 召回原因 |
|---|---|---|
| L2 | **L2-01 Traceability / 可追溯** | ① 时间线本质是资金可追溯凭证，升级后退居背景但不能丢；② 弱化时间线视觉权重的同时，保住"钱在哪、经历了什么、接下来去哪"。 |
| L2 | **L2-02 Honesty / 透明** | ① 页头展示实时汇率 6.8485 与到账 ¥6,848.50，属报价口径；② 明示汇率来源 / 时效 / 计价时点，避免对"到手多少"的口径疑虑。 |
| L2 | **L2-05 Distinction / 辨识** | ① 同屏出现 USD $1,000 与 CNY ¥6,848.50 两个币种；② 强对比区分汇出 / 汇入币种，防止看错金额。 |
| L2 | **L2-06 Trust / 可信** | ① 金额是这页的信任锚点，用户会核对"对不对得上"；② 让关键金额可信、可对账、可识别。 |
| L2 | **L2-07 Predictability / 可预期** | ① 催单类困惑的根源是"还要多久、跳过去会怎样"没被主动说；② 在用户开口前披露到账时效、跳转预期，主动消解焦虑。 |

### 1.3 L3 · 跨境汇款业务原则

| 层级 | 设计原则 | 召回原因 |
|---|---|---|
| L3 | **L3-Notify-01 一眼说清主体/事件/动作 + 唯一入口** | ① 自他收核心动作就是"通知"；② 把通知 CTA 做成单一明确入口，不让用户在多个模糊选项间犹豫。 |
| L3 | **L3-Notify-02 表达贴合场景与关系，熟人可用当事人口吻** | ① 自他收多为熟人代收；② 用贴合关系的口吻增强可信，更像"我在跟 TA 说话"。 |
| L3 | **L3-Notify-03 触达强度与阶段匹配，进行中主动推** | ① 交易正处进行中（waiting for setup）；② 此阶段主动推动"去通知"，而非完结后过度打扰。 |
| L3 | **L3-Notify-04 只承载最小必要信息，完整内容交落地页** | ① 已确认"收款人操作步骤外推给落地页"；② 这页只承载驱动汇款人去通知的最小信息 + 为何现在通知。 |
| L3 | **L3-Guide-01 关键操作前明确目标去向与事由** | ① 跳微信前用户需知道去哪、去干嘛；② 把"盲跳"变成"有准备的跳"。 |
| L3 | **L3-Guide-03 多角色场景兼顾各方视角与链路** | ① 自他收是汇款人 + 收款人多角色；② 这页只管汇款人链路、收款人链路交触达，分工不串台。 |
| L3 | **L3-Guide-04 跨平台跳转用最短路径 + 明确平台关系** | ① 痛点②本质是跨平台盲跳；② 最短路径跳转，并让用户明确"当前平台↔微信"的跳转关系与落点。 |
| L3 | **L3-Guide-06 完成任务的最低限度引导始终可见** | ① 无论处于哪个状态，用户都得随时看到"怎么往下走"；② 让核心引导不因状态切换而消失。 |
| L3 | **L3-Guide-07 主操作就近突出，次要操作降权** | ① 主 CTA 现被埋没；② 把主操作提到显眼位置，次要操作降权。 |
| L3 | **L3-Status-02 优先突出用户最关注的信息与待办** | ① 用户最关注"到哪了 / 还要做什么 / 钱在哪"；② 按此优先级重排信息，待办优先。 |
| L3 | **L3-Status-03 基于真实时效表达，处理中告知预计等待** | ① 用户想知道"还要多久"；② 精准表达时效、告知预计等待，压住催单类困惑。 |
| L3 | **L3-Status-04 非核心内容受控，仅在合适状态出现** | ① 升级后时间线等非核心内容需降噪；② 让非核心内容不干扰用户对"下一步"的关注。 |
| L3 | **L3-Select-02 选项标识多元、易识别，降低误选** | ① 现有 sharing sheet 提供微信/短信/又想/copy 多方式；② 让各分享方式易识别、可提炼默认最优，降低误选。 |

### 1.4 本次有意未召回（避免过度调用）

L2-03 披露、L2-04 安全，以及 L3 的授权确认 / 身份验证 / 提供信息 / 开通服务 / 合规判断——这些对应签约、鉴权、填单、开通、合规裁决类动作，本页不承载这些决策点，故不召回；若后续方案里真的引入（如跳转前二次身份确认），再补召。

## 2. 设计目标

### 2.1 核心问题

当前页面把"下一步该用户做什么"埋在时间线的一个节点里，且自收 / 他收共用一句 "Share to recipient"——导致自己收的人被"分享给别人"带偏、要去收款的人没被清楚推向"现在就通知"；同时用户对"点了会去哪、要多久"心里没底（盲跳）。页面停在"告知发生了什么"，没帮用户完成收款。

### 2.2 用户目标（体验为主）

- 进页 3 秒内知道：**现在轮到我，具体做这一件事**（自己领 / 通知 TA）。
- 跳去微信前，对"**会到哪、干嘛、大概多久**"有底，不是盲跳。
- 不再有"我到底该分享给谁 / 是不是操作错了"的那一秒犹豫。
- 在途仍能随时看清"钱在哪、到哪一步了"，不慌。

### 2.3 业务目标（体验做对后的自然结果，非出发点）

更高的下一步动作达成、更少的中途卡壳与"还要多久"类客诉。点击率 / 完成率 / 客诉下降是体验做对后的自然结果，不作为设计出发点。

## 3. 设计说明

### 3.1 信息架构（两场景共用骨架）

自上而下四段，A/B 只换内容不换骨架：

1. **顶部金额区**（信任锚点）：USD/CNY 强区分（币种色块 chip + "你付出 / 你将收到"标签）+ 汇率口径明示（"6.8485 · 已于 10:15 锁定为成交时点，到账不再变动"）。
2. **行动区 Hero**（页面新主角，从时间线里抽出）：状态 pill（多线索）+ "轮到你了" + 大标题动作 + 主 CTA + 兜底蓝链。
3. **交易进度时间线**（降权、默认折叠）：仅作可追溯背书，标题"交易进度 · 4/5 步，可追溯"，可展开看 5 节点，当前节点多线索表达。
4. **交易信息（可核对）**：收进 Details tab（Updates / Details 双 tab，Updates 放行动 + 时间线，Details 放交易信息）。

**自动分场景：** 进页判断收款人是否本人 → 决定 Hero 的标题动词（**领取** vs **通知**）、CTA、以及是否出现"跳转前预览"或"分享方式面板"。

### 3.2 场景 A · 自汇自收（差异点）

收款人 = 本人 → 主 CTA ＝「前往微信领取」（自己去收），配**跳转前预览**（打开微信 → 找到「XX汇款」对话 → 点「立即领取 ¥6,848.50」→ 进零钱，约 1 分钟到账），消除盲跳。标题动作指向"你自己领"，不出现"分享给别人"。

### 3.3 场景 B · 自汇他收（差异点）

收款人 = 他人 → 主 CTA ＝「通知李四收款」（推你去触达），点开 = 分享方式面板（微信标"推荐" + 短信 / 邮件 / 复制链接）。文案始终是"通知 TA"，不让你去替 TA 解释操作；收款人步骤由链接落地页承接（"领取步骤会在通知链接里告诉 TA，你无需转告"）。

### 3.4 降级方案

触发条件：ShareLink H5 中转 / 各渠道分享均不可用时。主 CTA 退化为「复制收款链接」，并保留「收款攻略」蓝链兜底，附链接安全提示（"含专属领取入口，请只发给李四本人"），绝不让页面变回只读状态页。

### 3.5 关键设计点 · 依据表

| 设计点 | 解决的问题 | 对应设计原则 |
|---|---|---|
| **行动区 Hero 从时间线中抽出，升为页面主角** | 主 CTA 原埋在时间线第 4 节点、与已完成节点同权，认不出、点不着 | L1-07、L1-13、L3-Guide-07、L3-Status-02 |
| **进页自动判断自收/他收，切换标题动词与 CTA**（领取 vs 通知） | 自收被"分享给别人"误导；他收没被推向"现在通知" | L1-08、L3-Notify-01、L3-Guide-03 |
| **自收：跳转前预览三步 + 预计到账** | 痛点②盲跳——不知道去微信到哪、做什么 | L1-05、L3-Guide-01、L3-Guide-04、L2-07 |
| **他收：文案只讲"通知 TA"，收款人操作步骤外推给链接落地页** | 页面越界替收款人解释、稀释汇款人主任务 | L1-03、L3-Notify-04、L3-Guide-03 |
| **他收：主 CTA 唤起分享面板**，微信标"推荐"，含短信/邮件/复制 | 熟人代收需贴合关系的一键触达；多渠道降低误选 | L3-Notify-01、L3-Notify-02、L3-Select-02 |

| **当前节点多线索表达**（琥珀色 + 脉冲圈 + "当前"文字标签） | 原"进行中"仅靠一个蓝点，单一线索易漏读 | L1-16、L3-Status-01 |

| **汇率口径明示**（"6.8485·已于10:15锁定为成交时点，到账不再变动"） | 用户对"到手多少"的口径疑虑 | L2-02、L2-07 |

| **预计到账时效前置**（Hero 与时间线未来节点均给"约1分钟/领取后"） | "还要多久"的不确定性催单 | L2-07、L3-Status-03 |

| **收款链接安全提示**（"含专属领取入口，请只发给李四本人"） | 专属收款链接误发给他人的资金风险 | L2-04、L1-11 |

### 3.6 两处「当前原则未覆盖」标注

1. **"进页自动识别自收/他收"的判定逻辑本身** —— 现有 L1/L2/L3 只覆盖"识别后如何分别表达"，但没有一条约束"用什么信号判定、判定错了怎么兜底"。**当前原则未覆盖**，建议补一条"场景自动判定需可纠错/可手动切换"。
2. **降级态里"复制链接"作为主动作的资金安全** —— 已按 L2-04/L1-11 关联"只发本人"提示，但"复制到剪贴板的专属收款链接如何防截留/防转发"更偏安全机制层，**现有体验原则只能覆盖到提示层，兜不住机制层**。

## 4. 设计反思（原则体系对"设计自驱类需求"的适用性评估）

> 核心结论：**现有原则在"把某一类服务做对"上很强，但在"判断一个页面该不该主动升级职责、多职责如何编排、以及'主动推进'本身该守什么"上偏弱**——而这恰恰是"设计自驱类需求"最吃的能力。

### 4.1 原则适用性

**能有效指导的部分（约 80% 的设计决策有据可依）：**
- 执行层判断几乎全程有原则兜底：CTA 认不出→L1-07、主次不清→L1-13、动作误解→L1-08、盲跳→L3-Guide-01/04、时间线降权→L3-Status-04、催单焦虑→L2-07、币种误读→L2-05。
- 分层结构好用：`L3→L2→L1` 逐层回看，每个决策都能追到上游依据；`冲突时怎么取舍` 这一栏在"时间线让位于行动区"时直接给了判断。
- 服务类型框架（前往→指引→行动+检验→结果）是个好用的镜头，帮助快速定位这页正在从"结果"长出"前往+指引"。

**指导不足的部分（方案里被迫"拼原则"或直接标注未覆盖）：**

| # | 指导不足之处 | 具体表现 |
|---|---|---|
| A | **一页承载多种服务类型时，如何定主次** | L3 用法前提是"先定位单一服务类型再引用"，但这页同时是 状态反馈 + 通知触达 + 前置指引。谁当页面主角没有页面级编排原则，只能靠 L1-13 + L3-Guide-07 手工拼。 |
| B | **"状态页可以升级为推进页"这件事本身** | 本需求命题核心无任何直接原则。L3-Status-02 只说"突出待办"，没说待办可强到凌驾状态展示、成为页面主 CTA。 |
| C | **系统自动判定（自收/他收）驱动的差异化 + 纠错** | 完全未覆盖：用什么信号判定、判定错了怎么被感知和纠正、判定不确定怎么兜底——空白。 |
| D | **能力不可用时的降级体验 + 涉资金链接安全** | L3-Guide-05 只覆盖"完成后出问题可补办"，没覆盖"分享能力挂了时页面不能退回只读、须保住最小可执行路径"；复制链接的防误发/防转发只能靠 L2-04/L1-11 勉强关联。 |

### 4.2 原则优化建议

| 现有原则 | 存在的问题 | 优化建议 |
|---|---|---|
| **L3 L3-Status-02**（突出最关注信息与待办） | 只说"突出待办"，未授权"待办可强到成为页面主操作、凌驾状态展示" | 补方向：**当存在明确、用户可立即执行的下一步时，行动待办优先于状态告知，可提升为页面主操作区** |
| **L3 L3-Guide-03**（多角色兼顾各视角各链路） | 只覆盖"各角色各看各的链路"，未覆盖"同一页面按场景/角色动态切换表达" | 扩展为：**同一入口服务多场景时，应按判定结果切换文案/CTA/信息优先级，而非共用一套通用表达** |
| **L3 L3-Guide-05**（完成后出问题可补办） | 只管"事后补办"，不管"能力降级时如何不损伤核心任务" | 扩展为：**降级/兜底时须保留核心任务的最小可执行入口，不得退回纯展示态** |
| **L3 L3-Notify-04 与 L3-Guide-01** | 两条都在讲"给进入判断的最小必要信息"，边界不清、易重复引用 | 明确分工：**L3-Notify-04 管"触达内容边界与外推"，L3-Guide-01 管"跳转前的目标认知"**；去重表述 |
| **L1-16 与 L3 L3-Status-01** | 一个在 L1（无障碍多线索）、一个在 L3（状态分层可辨），判断高度重叠 | **L3-Status-01 直接引用 L1-16，不再重述**，减少冗余 |

### 4.3 新增原则建议

**需要新增。** 现有 39 条 L3 集中在"每类服务内部怎么做对"，缺"页面级编排 / 主动推进 / 自动判定 / 降级"这四类跨服务类型的元约束，正好是自驱类需求的主战场。

| 建议新增原则 | 新增原因 |
|---|---|
| **【页面职责编排】页面同时承载多种服务类型时，应按"用户此刻最该完成的动作"确定唯一主职责，其余降为支撑** | 补 A：现体系"先定位单一服务类型"的前提在多类型页面失效，缺页面级仲裁规则 |
| **【行动优先】结果/状态类页面在存在明确下一步时可主动承担推进职责，行动区可凌驾状态展示成为主角** | 补 B：本需求"状态展示→交易推进"的命题核心目前无直接原则 |
| **【自动判定】页面依据系统判定切换表达时，判定须可被用户感知与纠正，且对判定失败/不确定提供安全兜底** | 补 C：自收/他收自动分场景是高频模式，当前完全空白 |
| **【降级体验】能力不可用时的降级不得损伤核心任务，须保留最小可执行入口；涉资金的分享/链接须防误发、防转发** | 补 D：把散落在 L2-04/L3-Guide-05 的碎片收敛为一条明确约束 |

（前两条建议放进一个新的"**页面级/编排层**"分组，因为它们约束的是"服务类型之间"的关系。）

### 4.4 原则质量评价

| 评价维度 | 评价 | 改进建议 |
|---|---|---|
| **完整性** | 中。单一服务类型内部覆盖扎实，但缺"多类型编排 / 主动推进 / 自动判定 / 降级"四类元约束 | 增设"页面级/编排层"分组，补 §4.3 的 4 条 |
| **一致性** | 良。分层清晰、`上游关联` 与 `冲突取舍` 格式统一；但存在重叠冗余（L2-06↔L3-Status-06、L2-01↔L3-Status-01、L1-16↔L3-Status-01、L3-Notify-04↔L3-Guide-01），易双重计数 | 建立"同一判断只在最具体层写一次，其余层引用编号"的去重规约 |
| **可理解性** | 优。`一句话 + 正反例 + 边界 + 冲突取舍` 结构非常好读，几乎无需额外解释 | 维持；新增原则沿用同一模板 |
| **可执行性** | **弱（最短板）**。原则都是"优先 X"的方向性判断，不是可检验的验收项，无法机械校验"这条满足了没"，能指路却不能 gate 产出 | 给关键原则配**检验点 / 验收清单 / 反面清单（anti-pattern）**，让"是否合规"可判定 |
| **可复用性** | 良。编号化 + 上游关联 + 服务类型框架为复用而设；但"先定位单一服务类型再引用"的假设在多类型页面失效，跨场景复用会断 | 补"按需求类型（推进类/告知类/纠错类…）预打包原则组合"的调用索引 |

### 4.5 最需要优先改进的三个方面

1. **补"页面级编排 + 行动优先"这一层（最紧迫）。** 判断"一页多职责谁当主角""状态页该不该升级为推进页"目前无据可依，只能手工拼 L1-13/L3-Guide-07。不补，同类需求每次都要重走一遍。
2. **把可执行性提上来：给原则配检验点与反面清单。** 现在原则是"方向"不是"闸门"，加上可判定的验收项和 anti-pattern，原则才能约束产出、支撑自校验。
3. **补"自动判定 + 降级兜底"两类真实高频但空白的场景约束。** 自收/他收自动分场景、分享能力降级、涉资金链接安全——都是这次实打实撞到"当前原则未覆盖"的地方，值得固化成原则。

---

**一句话总结：现有体系是一套优秀的"执行期判断手册"，但还不是一套"主动设计的决策框架"**——它能帮你把已知的一类服务做对，却还没能力指导"要不要、以及如何主动重塑一个页面的职责"。补齐编排层、抬升可执行性、覆盖自动判定与降级，这三步能把它从"手册"推向"框架"。
