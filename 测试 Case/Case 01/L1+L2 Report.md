# After Sending 交易推进页 · L1 + L2 原则驱动设计测试

> 本文件记录一次完整的「原则驱动设计」测试：从需求解读 → 原则召回 → 设计目标 → 方案与说明 → 对原则体系本身的反思。
> 本次仅调用 **L1 Universal（通用）+ L2 Cross-Border（跨境）** 两层原则，未使用 L3。
> 配套原型：[`after-sending-v1.html`](./after-sending-v1.html)（含自汇他收 3 态 + 自汇自收 1 态，支持中/英切换）。

---

## 0 ｜需求背景与理解

### 0.1 背景

国际汇款产品「After Sending · 汇款到微信」状态页：用户选择汇款到微信后，用于展示交易状态并引导完成后续收款。
现状以**状态展示**为主——顶部金额区（$1,000 → ¥6,848.50 + 实时汇率）、交易时间线、交易状态/子状态、收款通知（ShareLink / Share to recipient）。

**问题定位**：页面在"告知发生了什么"，而没有"帮用户完成下一步"。
**改造定位**：从「状态展示页」→「**交易推进页**」，在展示状态的同时主动推动收款完成。

**约束**：不新增后台能力；只靠信息架构 / CTA / 文案 / 交互；原型探索阶段，不受现有布局限制。

### 0.2 需求理解（经用户确认后定稿）

| 要素 | 结论 |
|---|---|
| **对象** | 一套**统一的「交易推进页」模板**，同时承载自汇自收 / 自汇他收（自汇自收页面尚未做，但必须是同一类型页，靠场景切换 CTA 与文案，而非两套页） |
| **用户群** | 全用户，不锁画像 |
| **问题** | 页面偏"告知"、主操作被埋、下一步不明确 →（推测）困惑 / 中断 / 客服。**无数据依据，全部按"设计推断"标注**，论证主要靠 L1/L2 站台 |
| **目标** | 让汇款人一眼知道"现在轮到谁、下一步做什么"并顺畅完成；**自收（我收到钱）与他收（对方收到钱）两者并重** |
| **约束** | 不新增后台能力；仅靠 IA／CTA／文案／交互；符合 L1+L2；不受现有布局限制 |

### 0.3 由确认带出的 3 个关键判断

1. **收款侧其实很轻**：收款人在微信直接看到通知卡片、点进去即可收款。故自汇他收的真正瓶颈**不在收款人**，而在**汇款人有没有把通知发出去、发给对的人/渠道**。
   - 但现状文案 `Waiting for LI SI to get setup on Weixin` 把"没发出去"包装成"在等对方设置"——**责任方说反，紧迫感被消解**。这是全案最尖锐的问题点。
2. **一套模板、两种"下一步"**：主行动区必须按场景变脸——自收=「去微信收款」，他收=「通知 TA 来收款」；两者并重，行动区在两场景都应是页面主角。
3. **没有数据 → 原则即论据**：本次不靠埋点，靠 L1/L2 逐条支撑取舍，保证可追溯、可复盘。

## 1 ｜原则召回

> 召回原则：只保留**决定设计方向的少数几条**（方向原则），把金额/币种/版式/无障碍等**执行原则**留到方案落地阶段，避免稀释重点。
> 最终调用 **4 条 L1 + 2 条 L2**。P0 = 跨境业务强相关。

### 1.1 L1 · 通用原则

| 层级 | 设计原则 | 召回原因（① 为什么需要 ② 解决什么 · 价值） |
|---|---|---|
| L1 | **L1-03** 先核心任务再补充 | ① 主操作（通知/去收款）被埋在时间线末端，主次倒置。② 把"此刻这一步"提为页面主角，时间线降级为辅助——推进页与状态页的分水岭。 |
| L1 | **L1-05** 知道在哪、下一步去哪（P0） | ① "状态页→推进页"整个命题就是它——用户须一眼知道现在到哪步、轮到谁、下一步做什么。② 本次绝对主轴，直接决定 IA 与"当前节点+下一步行动"的摆位。 |
| L1 | **L1-08** 理解当前动作和结果（P0） | ① `Waiting for LI SI to get setup` 把"你还没发通知"误述成"在等对方"，责任方错位——最尖锐问题点。② 用准确语言说清"现在什么状态、该谁做、做了会怎样"。 |
| L1 | **L1-02** 不牺牲理解与信任达成目标 | ① 目标是"提升点击率/完成率"，天然有催促、放大焦虑、诱导点击的风险。② 唯一护栏原则——划出"推进可以、施压不行"的边界，防止推进页变催收页。 |

### 1.2 L2 · 跨境原则

| 层级 | 设计原则 | 召回原因 |
|---|---|---|
| L2 | **L2-01** Traceability / 可追溯 | ① 时间线是"钱在哪、去哪"的载体，当前追溯链断且错。② 推进页的信任地基：让在途状态可感知，消解焦虑。 |
| L2 | **L2-07** Predictability / 可预期 | ① 时间线末端含 T+N、对方何时收等不确定项。② 平衡"催行动"与"安抚等待"，减少因未知而中断/问客服。 |

### 1.3 降级为"执行原则"（落地/评审时再用，不占方向召回）

L1-04 心智、L1-06 渐进披露、L1-07 可操作识别、L1-10 反馈、L1-12 一致性、L1-13 主次、L1-16 多线索状态；L2-02 汇率透明、L2-05 币种辨识、L2-06 金额可信。

## 2 ｜设计目标

- **核心问题**：页面止于"告知状态"，未回答"现在轮到谁、下一步做什么"；且 `Waiting for LI SI to get setup on Weixin` 责任方说反、消解紧迫感。
- **用户目标**：进页面 3 秒内知道"该我做什么"，一步完成（自收=去收款 / 他收=通知对方），且全程不焦虑。
- **业务目标**：提升行动卡 CTA 点击率与收款完成率——靠"把下一步说清楚"而非催促达成，减少困惑、中断与客服咨询。
- **关键策略**：
  1. 时间线从主角降为可展开的辅助信息（保留可追溯，不再压场）；
  2. 新增按场景变脸的「行动卡（Action Card）」作首屏主角；
  3. 修正误导文案，把责任方摆正；
  4. 一套模板承载两场景。

## 3 ｜设计说明

### 3.1 方案结构（原型：[`after-sending-v1.html`](./after-sending-v1.html)）

统一模板，自上而下：

```
金额头图  →  行动卡（Action Card，首屏主角）  →  进度（Step x/5，可展开完整时间线）  →  安全/预期条
```

- **共用结构不变**，**只有行动卡按场景变脸**：
  - 自汇他收：主 CTA =「Notify … on Weixin」，语义"把钱推给对方"；
  - 自汇自收：主 CTA =「Collect in Weixin」，语义"把钱收进自己钱包"。
- **连带差异**：头图（Send to LI SI / Your transfer；LI SI receives / You'll receive）、末节点（LI SI collects / in your wallet）、降级（他收=多渠道提醒+改发对象；自收=anytime 收款兜底，无对方变量、无需催）。

**覆盖状态**：
- 场景 A 自汇他收：A1 待通知（首屏核心）、A2 已通知待收款、A3 降级态（长时间未收款）；
- 场景 B 自汇自收：B1 待收款。
- 附中/英 UI 切换（`data-en`/`data-zh` + 顶部 EN|中 切换，实测通过）。

### 3.2 关键设计点 × 依据

| 设计点 | 解决的问题 | 对应设计原则 |
|---|---|---|
| **首屏「行动卡」**：金额下方即"轮到谁+下一步+主CTA"，时间线后置 | 主操作被埋在时间线末端，主次倒置 | L1-03、L1-05 |
| **CTA 按场景变脸**：他收=Notify on Weixin／自收=Collect in Weixin，其余结构不变 | 一套模板承载两场景，且两者并重 | L1-05（下一步明确） |
| **修正误导文案**：`Waiting for LI SI to get setup` → `LI SI hasn't been notified yet · it's on you` | 责任方说反、动作与结果错位（最尖锐问题） | L1-08 |
| **进度压缩为「Step 4 of 5」+ 可展开时间线** | 六段系统步骤信息过载、掩盖当前状态 | L1-05（当前位置）；L2-01（可追溯不丢） |
| **"On its way / usually within minutes" 预期披露** | 在途 pending 含 T+N、对方何时收等不确定项 | L2-07 |
| **安全兜底条**："money is safe / fully tracked / nothing lost while you wait" | 在途焦虑；他收对方不可控 | L2-01、L2-07 |
| **不用倒计时/施压，只提供"再次提醒/换渠道/改发对象/联系客服"** | 目标是提升点击，但不能靠放大焦虑诱导 | L1-02（护栏）；L2-04（发错对象防错） |
| **降级态 A3**：久未收款→多渠道提醒 + Resend + 客服自助 | 卡住时无出路，转而问客服 | L1-02、L2-04、L2-07 |
| **自收去除一切"通知别人"措辞**：Your transfer／You'll receive／collect anytime | 自收套用他收文案会产生误解 | L1-08、L1-05 |

### 3.3 需标注的落地前提

- **「行动卡以视觉容器顶到首屏」** 属对既有原则的执行落地；视觉层级细则（L1-13）为执行原则，方向层不占位，此处如实说明。
- **「Resend to someone else / 改发收款对象」** 按前端交互列入，但**是否放开改发对象可能触及后台能力**——若属新增能力则超出"不新增后台"约束，**当前约束下需确认可行性**（本案唯一有落地前提的设计点）。

## 4 ｜设计反思（对 L1+L2 原则体系的评估）

> 评估问题：现有原则能否有效指导**设计自驱类需求**（主动重构去推动任务，而非修 bug / 补痛点）。

### 4.1 原则适用性

- **能有效指导**：本次绝大多数**防守型判断**都被稳稳接住——主操作前置（L1-03/05）、修正误导文案（L1-08）、在途预期与安全（L2-07/01）、一套模板两场景（L1-05）。说明体系在**理解、防错、可追溯、可预期**上成熟。
- **指导不足**（本次实打实撞到的空白）：
  1. **缺"主动推进/助推"维度**：核心命题"从告知→推进"找不到正面原则背书，现有最多说到"别让用户迷路"，没有"主动帮用户往前推"。「行动卡作首屏主角」只能当执行层处理。
  2. **"推动行动"缺可执行伦理护栏**：目标含转化指标，易滑向虚假紧迫/暗黑模式；全程只能拿 L1-02 兜，但它太宽，判不了"倒计时算不算越界"。
  3. **"责任方归属"无对应原则**：最高价值改动（改误导文案）靠 L1-08 勉强兜住，但 L1-08 讲"动作/结果清楚"≠"责任主体清楚"。
  4. **"降级/等待态"无专门支撑**：A3 只能拼 L2-07+L2-04。

### 4.2 原则优化建议

| 现有原则 | 存在的问题 | 优化建议 |
|---|---|---|
| **L1-02** 不牺牲理解与信任 | 太宽泛，是价值观非可执行边界，判不了具体诱导手段是否越界 | 补可操作清单：列明禁用手法（虚假紧迫、隐藏退出、默认勾选…），把护栏从态度变清单 |
| **L1-08** 理解当前动作和结果 | 覆盖"动作/结果"但未显式覆盖"责任主体" | 核心判断增补"进行中状态须明示责任方（用户/平台/对方）" |
| **L2-07** Predictability | 讲了"披露不确定性"，但对等待/卡住/降级态无落点 | 扩展适用场景纳入停滞/超时/失败态，并要求同时给出"此刻可做的补救动作"，与 L2-04 打通 |
| **L2-02 / L2-06 / L2-05** 透明·可信·辨识 | 三条语义高度重叠，召回时反复权衡 | 明确分工（口径来源 / 可对账 / 多币种防混淆）并补齐各自"不适用场景" |
| **L2-04 vs L1-11** 防错可退 | 两条几乎同义、跨层重复 | L1-11 讲通用防错，L2-04 只讲跨境不可逆资金后果，去重 |

### 4.3 新增原则建议

需要新增——本次需求核心恰落在体系空白区，不新增则自驱类需求缺方向层依据。

| 建议新增原则 | 新增原因 |
|---|---|
| **主动推进 / 助推（建议 L1）**：状态/进程类页面不应止于"告知"，应主动呈现"当前该做的下一步"并降低其执行成本，把用户从被动知情转为主动推进 | "状态页→推进页"整个命题无正面原则支撑；这是所有自驱型改版的共性方向 |
| **责任方明确（建议 L1，或并入 L1-08）**：任何进行中状态必须让用户一眼看出"现在轮到谁、卡在哪一方" | 全案最高价值改动无直接背书；责任错位是状态类页面高频陷阱 |
| **助推的伦理边界（建议 L1，作 L1-02 可执行延伸）**：推动行动时禁用虚假紧迫、施压、遮挡与暗黑模式，只能靠"把价值和下一步说清"提升转化 | 自驱需求普遍带转化指标，天然有滑向 dark pattern 的动力；现有只有价值观、无红线 |

> 不建议单列："降级/等待态设计"更适合**并入 L2-07 扩展**，避免体系膨胀。

### 4.4 原则质量评价

| 评价维度 | 评价 | 改进建议 |
|---|---|---|
| **完整性** | 防守型维度完整；**自驱型维度（主动推进、责任归属、助推伦理、降级态）缺失**，本次最大短板 | 补 2–3 条 L1，覆盖"从告知到推进"的正向指导 |
| **一致性** | 分层清晰、可追溯；但 **L2 内部（02/06/05、04 vs L1-11）语义重叠**，跨层职责边界不干净 | 做一次去重与分工界定 |
| **可理解性** | "一句话+正反例+冲突取舍"好读；L1 每条 7 字段偏长，扫读成本高 | 另出"一句话+冲突取舍"速查卡供召回用 |
| **可执行性** | "冲突时怎么取舍"极实用；但自驱需求下只能给方向、给不出模式（行动卡/降级态需自己发明） | 靠 L3 补业务模式；正例中增加"推进型"样例 |
| **可复用性** | 编号+适用/不适用+取舍结构可复用性强；部分"不适用场景"偏薄或空 | 强制补齐每条"不适用场景"，尤其重叠原则 |

### 4.5 最需优先改进的三个方面

1. **补齐"主动推进"维度**：体系整体偏防守，缺支撑"从告知到推进"的自驱原则——正是本次核心命题、也是这类改版的通用诉求。**第一优先。**
2. **给"推动行动"配可执行伦理护栏**：自驱需求都带转化指标，L1-02 太宽管不住手段，需列明红线（虚假紧迫/暗黑模式）的原则。
3. **消冗余、明边界**：L2 内部及 L2-04↔L1-11 的重叠导致召回反复权衡、一致性受损；配合补齐"不适用场景"，可同时提升一致性、可执行性与可复用性。

> **一句话结论**：现有原则**善于兜底"别做错"，不擅长指导"主动做得更好"**。对设计自驱类需求，它能审查方案、却给不出方向——补上"主动推进 / 责任归属 / 助推伦理"三条，是让原则体系真正驱动自驱设计的关键。
