## 1. 前往 · 🟤 通知触达（5）

> 平台主动向用户触达信息。
> 触点：分享卡片 · 短信 · 公众号消息 · 收款页调单 banner

| 编号 | 原则 |
| --- | --- |
| 通知-01 | 触达应一眼说清主体、事件与所需动作，并给出唯一明确入口 |
| 通知-02 | 触达的表达应贴合场景与双方关系，熟人场景可用当事人口吻增强可信与转化 |
| 通知-03 | 触达强度应与事件紧迫度和所处阶段匹配，进行中主动推送、已完结轻提醒，避免过度打扰 |
| 通知-04 | 触达只承载驱动决策与进入的最小必要信息，并点明行动的利益或后果及其时限，完整内容交落地页承接 |
| 通知-05 | 用户可能不了解本平台时，触达应展示官方身份与背书，降低信任门槛 |

## 2. 指引 · ⚫ 前置指引（7）

> 在关键操作发生前提供说明与引导。
> 触点：Sharelink 收款指引 · 自然开户引导 · 风控调单解脱 · 留学缴费转账指引

| 编号 | 原则 |
| --- | --- |
| 指引-01 | 关键操作前应明确目标去向与事由、操作事项及前置条件 |
| 指引-02 | 多步骤引导应先建立整体流程认知，再连贯分步展开 |
| 指引-03 | 多角色场景应兼顾各方视角与各自链路 |
| 指引-04 | 跨平台跳转应采用最短路径，并让用户明确当前平台与目标平台的跳转关系 |
| 指引-05 | 操作完成后若出现问题，应支持补办并明确待补内容与入口 |
| 指引-06 | 完成当前任务所需的最低限度引导应始终可见 |
| 指引-07 | 主操作应就近突出，次要操作降低权重 |

## 3. 行动 · 🟢 授权确认（4）

> 用户对规则、协议、权限作出明确同意。
> 触点：开户签署协议 · 新增渠道补签 · 留学缴费签署 · 首次接收确认

| 编号 | 原则 |
| --- | --- |
| 授权-01 | 协议须由用户主动勾选而非默认，未勾选提交时应提示而非置灰 |
| 授权-02 | 需签署的协议应尽量一次性签完，避免分散多次 |
| 授权-03 | 协议可默认折叠，用户可自行展开查看 |
| 授权-04 | 重复性授权只需首次确认，后续可自动执行 |

## 4. 行动 · 🔴 身份验证（1）

> 平台核实操作者为本人及身份合法。

| 编号 | 原则 |
| --- | --- |
| 验证-01 | 身份验证方式应匹配业务风险并轻量优先（微信密码 > 短信 > 刷脸） |

## 5. 行动 · 🟠 选择方式（4）

> 用户在多个可选项中做出决策。
> 触点：选择汇款机构 · 选择收款方式 · 选择付款方式

| 编号 | 原则 |
| --- | --- |
| 选择-01 | 应聚合提炼关键决策信息，帮助用户判断当前最优方式 |
| 选择-02 | 查找路径与选项标识应多元、易识别，降低误选 |
| 选择-03 | 介绍备选项时应先建立信任，再引导选择 |
| 选择-04 | 决策信息不可得时应提供兜底说明，不留空白 |

## 6. 行动 · 🔵 提供信息（7）

> 用户向平台录入或补充所需材料。
> 触点：汇款填单 · 开户完善个人信息 · 护照完善姓名 · 风控调单提交材料 · 留学缴费填写

| 编号 | 原则 |
| --- | --- |
| 信息-01 | 关键数值应完整、准确呈现 |
| 信息-02 | 输入超限或不合规时应即时、明确提醒并引导修正 |
| 信息-03 | 材料与字段要求应明确并配范例或对照，必要时提供客服兜底，帮助用户按要求准确提交 |
| 信息-04 | 跨页填写应减少重复录入与转译负担 |
| 信息-05 | 应只收集必要信息，字段依据真实业务要求确定 |
| 信息-06 | 收集信息应说明依据与用途，并保障隐私安全 |
| 信息-07 | 关键信息提交前应支持核对确认，降低填错 |

## 7. 行动 · 🟣 开通服务（3）

> 激活一项此前未具备的新功能。
> 触点：开通侨汇优先服务 · 服务管理与关闭 · 额度查询

| 编号 | 原则 |
| --- | --- |
| 开通-01 | 开通前应讲清价值与使用条件，并将所需步骤前置、一次完成 |
| 开通-02 | 已开通的服务应可见状态，并支持管理与关闭 |
| 开通-03 | 服务的关键约束应可查，超限或不可用时提供兜底 |

## 8. 检验 · ⚪ 合规判断（2）

> 平台在后台对用户信息进行合规裁决；设计负责如何披露裁决结果并引导用户解决。
> 触点：实名认证 · 证件校验 · 收款人一致性校验

| 编号 | 原则 |
| --- | --- |
| 合规-01 | 合规要求应前置披露并说明依据，不在用户提交后才暴露 |
| 合规-02 | 合规校验不通过时应说清原因、符合范围、补救路径与后果 |

## 9. 结果 · 🟡 状态反馈（6）

> 用户获取当前业务所处的进度或结果。
> 触点：收款订单详情页 · 到账/审核结果 · 异常状态解脱

| 编号 | 原则 |
| --- | --- |
| 状态-01 | 状态应真实、分层可辨，以一致视觉线索区分 |
| 状态-02 | 应优先突出用户最关注的信息与待办，其余信息按优先级组织 |
| 状态-03 | 结果应基于真实时效精准表达，处理中应告知预计等待时间 |
| 状态-04 | 非核心内容应受控，仅在合适状态出现，避免干扰用户关注结果 |
| 状态-05 | 异常或失败应说明原因、时限与资金去向 |
| 状态-06 | 应完整展示关键交易信息，支持核对与追溯 |
