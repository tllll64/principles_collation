# 微汇款服务类型分类 · 四方评审总结

> **评审对象**：微汇款9类服务类型 + 通用服务框架「前往 → 指引 → 行动 + 检验 → 结果」
> **参与模型**：Claude Opus 4.8、DeepSeek V4 Flash、GPT 5.6 Sol、Kimi K3
> **汇总日期**：2026-07-23

## 总览

| 评审模型 | 综合评分 | 定位判断 | 最看重的问题 |
|---|:---:|---|---|
| Claude Opus 4.8 | **86**（A-） | 骨架已很好，可直接指导设计 | Happy Path，缺异常态 |
| DeepSeek V4 Flash | **82** | 抽象层次选得对，覆盖「走通」路径 | 缺异常 + 缺「中断续办」 |
| GPT 5.6 Sol | **80** | 是「任务节点模型」，被误命名为「服务类型模型」 | 分类层级混杂 + 异常缺失 |
| Kimi K3 | **76** | 内部分析成果优良，团队通用框架还差四块拼图 | 主体混链 + 缺设计产出映射 |

## 一、各模型评审要点

### 1. Claude Opus 4.8 — 86分（最高分）

**优点**
- 抽象层级统一（93分）——最难也最亮，无「大类混小类」的塌陷
- 「前往→指引→行动+检验→结果」是可迁移的黄金框架，用「+」表达并行/嵌套
- 把「合规判断」单独立类，抓住金融业务的灵魂
- 色彩编码 + 频率/参与度双标签，信息密度高、可直接指导排期

**缺点/隐患**
1. 【最大隐患】整套为 "Happy Path"，缺失异常态（状态/容错覆盖仅71分）
2. 「接收通知」与「前置指引」边界偏软
3. 缺「确认/复核」类，被隐性塞进流程里
4. 「开通服务」样本单薄（仅1场景），有过度抽象风险
5. 命名的动作主语（用户/平台）不统一

**可改进项**
- 定义完整状态机：处理中 / 成功 / 失败 / 需补件 / 已驳回
- 新增或明确「异常处理」「确认复核」两类的归属
- 收敛🟤与⚫的归类判据，表头标注每类的动作发起方
- （补完即可从 A- 迈向 A+）

### 2. DeepSeek V4 Flash — 82分

**优点**
- 抽象层级合适、复用性强（五段式框架在差异较大的业务上都走得通）
- 「行动+检验」并行结构抓住金融「前台操作、后台风控」的双轨本质
- 分色系统降低跨角色沟通成本
- 需求频率 × 设计参与度的二维标注
- 从真实业务流反推验证（归纳而非先验）

**缺点/隐患（带扣分）**
1. 缺少错误/异常/兜底路径（-8）※最大问题
2. 「接收通知」归入「前往」有认知偏差（-4）
3. 频率/参与度缺少客观依据（-3）
4. 「开通服务」作为独立类支撑太弱，仅1个用例（-2）
5. 线性流程无法覆盖「中断-续办」场景（-3）
6. 部分类型边界模糊（-2）
7. 「汇款」场景验证不足（-1）

**可改进项**
- 补「异常处理类」：拒绝、失败、超时、补件、申诉
- 补「中断续办类」：存盘退出、进度保存、回访入口
- 为频率数据补来源，或标注「估计值，待验证」

### 3. GPT 5.6 Sol — 80分

**优点**
- 从真实业务归纳（非模型先行）
- 抓住金融核心「用户行动与平台检验并行」
- 提炼「查看状态」= 具备异步服务意识
- 覆盖多角色、跨用户接力
- 框架简洁、适合团队传播
- 对设计资产沉淀有直接帮助
- 「频率×参与度」有管理价值

**缺点/隐患**
1. 最大问题：9类不完全处于同一分类层级（触发方式 / 信息支持 / 用户任务 / 认证机制 / 业务目标 / 后台机制混在一起）
2. 类型之间不互斥（一个页面同时承担多任务，更像标签体系而非单选分类）
3. 颗粒度不一致（「提供信息」是原子动作，「开通服务」是完整业务流程）
4. 文档中已出现的动作（分享、邀请、转交等）未被归纳
5. 通用框架过于线性
6. 「结果」被收窄成「查看状态」
7. 「合规判断」易变成用户不可理解的后台黑盒
8. 频率/参与度缺量化口径
9. 缺正常流与异常流的显式区分

**可改进项（核心建议）**
- 校准对外定义：「9类服务类型」→「9类通用服务任务节点」
- 框架改表述为：触发/进入 → 理解与准备 → 用户行动 ⇄ 平台检验 → 结果反馈与后续处理
- 一句话诊断：**内容没错，但它本是「任务节点模型」，却被命名成了「服务类型模型」**

### 4. Kimi K3 — 76分（最低分，最辛辣）

**优点**
- 以「用户行为」为原子（而非页面/业务模块），使跨业务同构比较成为可能
- 把平台侧节点⚪合规判断纳入体验链路（服务蓝图思维）
- 频率 × 参与度双维标注直指资源分配
- 框架压缩能力强、沟通成本低
- 方法论方向正确（先归纳、再回代验证）

**缺点/隐患**
1. 行为主体混在一条链上（最核心问题）→ 建议分用户/平台泳道
2. 类型边界有重叠，缺判定规则
3. 「接收通知/功能入口」合并掩盖了关键差异（被动触达 vs 主动进入）
4. 只覆盖 happy path，缺异常与回退类型
5. 频率无数据来源 +「设计参与度」缺操作定义
6. 记号语义（[ ]、+、/）未定义，团队协作会漂移
7. 汇款业务偏置未检验、无治理规则（有腐化风险）
8. 缺「分类→设计产出」映射层（影响最大的落地缺口）

**可改进项（带优先级）**
- ④异常分支补全 ＞ ①泳道分离 ＞ ⑧设计产出映射 ＞ ⑤数据校准
- 补充争议：🟡查看状态参与度标「中」，实际应为「高」（等待到账是情绪峰值时刻）

## 二、横向对比：共识与差异

### 四方共识（表述不同但高度一致）

| 共性问题 | DeepSeek | GPT | Claude | Kimi |
|---|:---:|:---:|:---:|:---:|
| 异常/失败路径缺失（公认最大问题） | ✅ | ✅ | ✅ | ✅ |
| 「接收通知」分类不当 | ✅ | ✅ | ✅ | ✅ |
| 「开通服务」支撑薄弱（仅1场景） | ✅ | ✅ | ✅ | ✅ |
| 频率/参与度无客观数据 | ✅ | ✅ | — | ✅ |
| 边界模糊 / 缺判定规则 | ✅ | ✅ | ✅ | ✅ |

### 各家独特视角

- **Claude**：唯一独家点出缺「确认/复核」类；评价最正面，认为「骨架已经很好」。
- **DeepSeek**：独家点出「中断-续办」场景缺失（准备材料、等银行流水、线下盖章等需存盘退出）。
- **GPT / Kimi**：强调更根本的结构问题——分类层级/主体混杂（GPT = 命名定位错误，Kimi = 主张泳道分离）。
- **Kimi**：唯一点出「分类→设计产出映射层」这个从「分析成果」走向「设计资产」的生产性缺口。

### 规律

分数越低的模型，越从「结构、治理、落地」等根本层面严格要求；分数越高的模型，越肯定其抽象与骨架价值。

## 三、综合改进路线图（四方观点整合）

按优先级排序：

1. **补齐异常/负向分支（四方一致的首要项）**
   - 定义完整服务状态机：处理中 / 成功 / 失败 / 需补件 / 已驳回 / 超时 / 撤销退款
   - 明确「合规驳回 → 补件 → 再判断」的回流路径归宿
   - 将「查看状态」从单一结果扩展为「结果反馈与后续处理」

2. **校准分类定位与层级**
   - 对外定义改为「通用服务任务节点 + 标签体系」，而非单选式「服务类型」
   - 分用户侧 / 平台侧泳道，显性化「行动+检验」中已隐含的主体区分
   - 统一命名的动作主语，表头标注每类的发起方（用户/平台）

3. **修补具体类型的边界**
   - 拆分/明确「接收通知」（被动触达 vs 主动入口）
   - 补「确认/复核」类的归属
   - 重新审视「开通服务」是否为通用原子（否则降级为组合）
   - 为易混类型补「判定规则」（当X时归A不归B）

4. **补落地与数据**
   - 建「分类 → 设计产出」映射层（如 提供信息→表单规范、授权确认→协议弹窗模板）
   - 频率/参与度用埋点/订单量校准，明确「设计参与度」= 需要投入 or 现状投入
   - 补一页记号图例（[ ]、+、/ 的语义）

5. **补场景与治理**
   - 补「中断-续办」维度（存盘退出、进度保存、回访入口）
   - 补「汇款侧」及非汇款场景验证，建「何时新增类型 vs 归入已有」的治理规则
