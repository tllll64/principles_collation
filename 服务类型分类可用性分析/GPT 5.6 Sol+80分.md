# 微汇款服务类型分类评审

- **评审模型：** GPT 5.6 Sol
- **综合评分：** 80 / 100
- **评审视角：** 高级体验设计专家
- **评审对象：** 微汇款9类服务类型及通用服务框架

## 一句话结论

这套分类**作为“跨业务通用体验任务模型”已经基本成立**，能够支持流程分析、设计模式沉淀和设计资源分配；但如果把它定义为严格的“服务类型分类”，目前存在明显的**分类层级混杂、边界重叠和异常链路覆盖不足**。

更准确的定位建议是：

> **微汇款9类服务任务节点，以及“前往—指引—行动与检验—结果”的通用服务框架。**

## 评分拆解

| 评估维度 | 分数 | 评价 |
|---|---:|---|
| 业务覆盖完整度 | 18/20 | 覆盖汇款、收款、开户、调单、留学缴费、代付等核心业务 |
| 抽象与归纳能力 | 18/20 | 能从复杂业务中收敛出稳定的通用主链路 |
| 用户旅程解释力 | 16/20 | 能解释主流程，但对分支、循环、跨角色接力表达不足 |
| 分类严谨性 | 12/20 | 分类项不完全同层，存在重叠和颗粒度差异 |
| 设计落地价值 | 16/20 | 对页面模式、组件、设计投入和体验走查有较高价值 |
| **总分** | **80/100** | **框架成立，分类体系仍需收敛** |

# 优点

## 1. 从真实业务归纳，而不是先有模型再套业务

文档先拆解了全球汇入—汇款、全球汇入—收款、自汇自收、自汇他收、风控调单、留学缴费和亲友代付等具体链路，再反向提炼共性。这种自下而上的方法，使9类节点具有较强的业务依据，而不是停留在概念层面。

## 2. 抓住了金融服务的核心：用户行动与平台检验并行

框架中的：

> **行动 + 检验**

是最有价值的抽象。普通互联网流程通常是“进入—操作—完成”，但微汇款业务始终伴随身份、限额、材料、风控和合规判断。把检验独立出来，符合金融业务的真实结构。

## 3. 已经具备“异步服务”意识

将“查看状态”单独提炼出来，说明没有把“提交成功”直接等同于“服务完成”。微汇款普遍存在等待审核、等待银行处理、等待对方操作、等待到账、等待补充材料和异常后重新处理，因此状态反馈确实应成为通用能力。

## 4. 覆盖了多角色和跨用户接力

对自汇他收、亲友代付等场景进行了不同角色视角拆分，说明模型不局限于单用户单端流程。这对于微汇款很重要，因为很多链路实际上是：

> 发起人操作 → 分享或通知 → 另一角色承接 → 平台检验 → 双方查看结果

## 5. 框架简洁，适合团队传播

“前往—指引—行动—检验—结果”有较强的记忆性，可以快速帮助设计师判断：

- 用户为什么来到这里；
- 当前是否需要解释；
- 当前要求用户做什么；
- 平台在判断什么；
- 用户最后需要知道什么。

作为团队通用分析语言，这一点很有价值。

## 6. 对设计资产沉淀有直接帮助

其中几类特别适合继续形成标准体验模式：

- 授权确认模式；
- 身份验证模式；
- 方式选择模式；
- 信息填写模式；
- 合规审核模式；
- 状态反馈模式。

未来可以对应页面模板、组件、文案规则、状态模型和设计走查清单。

## 7. 增加“需求频率 × 设计参与度”具有管理价值

这不仅是在做体验分类，也在尝试判断设计投入优先级。例如“提供信息”“合规判断”同时具有高频率和高设计参与度，确实应优先进行体验标准化。

# 缺点及隐患

## 1. 最大问题：9类不完全处于同一个分类层级

当前分类混合了多种性质：

| 类型 | 实际性质 |
|---|---|
| 接收通知 | 触发事件或触达方式 |
| 前置指引 | 信息支持行为 |
| 授权确认、选择方式、提供信息 | 用户任务 |
| 身份验证 | 安全与认证机制 |
| 开通服务 | 业务目标或生命周期变化 |
| 合规判断 | 平台后台机制 |
| 查看状态 | 用户查询行为 |

因此，它们并不是严格并列的“服务类型”。例如“开通服务”本身可能同时包含授权确认、身份验证、提供信息和合规判断。

**潜在隐患：**当团队用这套分类进行需求归档时，会出现“一个需求到底归哪类”的争议。

## 2. 类型之间不是互斥关系

同一个页面或步骤可能同时承担多个任务：

- 确认页：授权确认 + 信息复核；
- 开户页：提供信息 + 身份验证；
- 方式选择页：选择方式 + 前置指引；
- 审核页：合规判断 + 查看状态；
- 开通流程：授权 + 验证 + 填写 + 判断 + 结果。

这并不代表分类错误，但说明它更适合作为**节点标签体系**，而不是每个节点只能选一个的单选分类。

## 3. 类型颗粒度不一致

“提供信息”是一个较原子的动作；“开通服务”却是一段完整业务流程。

同样，“授权确认”目前也混合了不同含义：

- 同意协议；
- 授权平台使用信息；
- 确认业务规则；
- 确认支付或汇款；
- 确认由亲友代付。

这些场景的法律含义、风险等级和体验要求都不同。

## 4. 尚未覆盖文档中已经出现的部分动作

流程中存在一些没有被9类明确归纳的步骤：

- 功能入口；
- 点击“我要收款”；
- 分享卡片；
- 分享给收款人或亲友；
- 确认信息；
- 支付金额；
- 返回修改或重新提交。

这表明9类暂时还没有完整覆盖所有业务节点。尤其“分享、邀请、转交”在微汇款多角色业务中比较重要，不能只作为普通操作文字存在。

## 5. 通用框架过于线性

真实业务并非总是：

> 前往 → 指引 → 行动 + 检验 → 结果

更常见的是：

> 触发 → 行动 → 判断 → 等待 → 补充 → 再判断 → 跨角色接力 → 结果

当前框架对条件分支、多次合规判断、审核驳回、补充材料、返回修改、跨角色等待、超时重试和流程恢复表达不足。

**潜在隐患：**团队可能把主干框架误当作标准线性流程，降低对异常和恢复路径的重视。

## 6. “结果”被收窄成了“查看状态”

“查看状态”仍然是用户动作，不是完整的服务结果。结果层至少应该回答：

1. 发生了什么；
2. 当前资金处于什么状态；
3. 为什么是这个结果；
4. 预计什么时候完成；
5. 用户下一步做什么；
6. 是否可以修改、重试或申诉。

建议将“查看状态”提升为：

> **结果反馈与后续处理**

“查看状态”可以作为其中一种具体行为。

## 7. “合规判断”容易变成用户不可理解的后台黑盒

如果只定义为“平台后台裁决”，设计容易止步于“审核中”“审核失败”“系统判断不通过”或“请补充材料”。但用户真正关心的是：

- 为什么需要审核；
- 当前检查到哪里；
- 为什么没有通过；
- 资金是否已经扣除；
- 需要补充什么；
- 预计多久完成；
- 是否可以重试或申诉。

因此，合规判断最好同时包含“判断机制”和“面向用户的解释与恢复”。

## 8. “需求频率”和“设计参与度”缺少量化口径

目前的高、中、低更像经验判断，尚未说明是按需求单数量、用户触发次数、覆盖业务数量、页面数量，还是设计投入工时统计。

另外，低频不代表低优先级。例如身份验证频率可能不高，但属于资金安全关键节点，设计风险很高。

## 9. 缺少对“正常流”和“异常流”的显式区分

当前模型主要来自正常业务主链路，但金融体验的质量往往由异常流决定：

- 验证失败；
- 合规拒绝；
- 额度不足；
- 材料不完整；
- 支付成功但订单未更新；
- 对方未操作；
- 汇款退回；
- 页面中途退出。

如果后续用这套分类做体验治理，异常和恢复应成为单独的检查维度，而不能完全依附在9类节点中。

# 最终建议

保留现有成果，但建议调整对外定义。

### 当前定义

> 9类服务类型

### 更准确的定义

> **9类通用服务任务节点**  
> 用于描述微汇款业务中用户与平台分别承担的任务，以及这些任务在服务流程中的组合关系。

通用框架可以继续保留，但建议表达为：

> **触发/进入 → 理解与准备 → 用户行动 ⇄ 平台检验 → 结果反馈与后续处理**

这样既保留现有框架的简洁性，又能容纳循环、异常、等待与恢复。

## 评审结论

这套分类已经具有较高的设计实践价值。主要问题不是“分类内容错了”，而是：

> **它实际上是任务节点模型，却被命名成了服务类型模型。**

把定位校准后，整体成立度会明显提升。
