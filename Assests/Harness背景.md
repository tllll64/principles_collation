# FiT 设计组 AI 转型共识：Harness 三层架构

> 这份文档用于沉淀 FiT 设计组当前关于 AI 设计生产 Harness 的团队共识。它重点说明为什么要做 Harness、Harness 应该如何分层、每一层承担什么职责，以及下一阶段设计生产建设的聚焦方向。

## 1. 我们为什么要做这件事

部门当前正在准备部门级别的 Harness 工程设计，希望让 AI 从整体到具体生产环节都能理解业务，并提升设计与生产效率。

上一阶段，各个环节或个人已经开始搭建 skill，但整体更偏线性工作路径逻辑，主要解决单点问题。对于复杂设计生产场景，仅靠单点 skill 并不科学。

例如，生成一个设计方案时，AI 不应该只调用某个“页面生成 skill”。它还需要理解用户洞察、业务规则、已有体验流程、UI 组件、视觉要求和设计原则。也就是说，复杂环节需要系统性的架构建设，而不是只堆叠一个个独立 skill。

因此，当前阶段需要更聚焦地解决设计环节中的 AI 生产问题，尤其是页面生产和 UI 方案生成方面的建设。

本阶段重点讨论两件事：

1. 明确下一阶段聚焦设计生产 Harness 搭建，尤其是页面生产和 UI 方面的建设。
2. 确认新的 Harness 架构，并明确各层职责与分工。

## 2. 我们要造什么：Harness 三层架构

Harness 的核心思路，是把 AI 设计能力拆成三层，各自职责清晰、互不重叠。

| 层级 | 一句话 | 内容类型 |
| --- | --- | --- |
| 应用层 / 动词 | AI 做什么事 | 业务整体 skill |
| 原则层 / 形容词 | 怎样才算好 | 设计哲学、规则、取舍准则 |
| 资料层 / 名词 | 有什么素材 | 组件库、用研、案例、业务规则 |

## 3. 三层关系

```text
应用层（Skills）       负责调用和执行
        ↑
原则层（Principles）   负责约束和判断
        ↑
资料层（Materials）    负责提供事实和素材
```

当设计师触发 skill 时，应用层负责理解任务并组织动作；资料层提供事实依据，例如组件、用研、案例和业务规则；原则层提供判断规则和取舍标准，约束 AI 产出方案。

一个简单比喻：

- 资料层 = 设计师的工具箱和素材库。
- 原则层 = 设计师的脑子和判断力。
- 应用层 = 设计师的一双手。

没有原则层，AI 可能会出“页面对、架构错”的稿。没有资料层，AI 可能会凭空编造。没有应用层，资料和原则无法进入真实生产流程。三者缺一不可。

## 4. 资料层：Materials

资料层定位为事实库，只放“事实”，不放“判断”。

一条铁律：

资料层绝不写“我们应该如何”，因为那是原则层的事。资料层只回答“是什么”。

一期必做内容：

| 序号 | 内容 | 说明 |
| --- | --- | --- |
| 1 | UI 原子样式和组件 | Figma 组件库、Token JSON、全状态 |
| 2 | 用户洞察、画像、问卷 | 8 类画像、深访、问卷结构化入库 |
| 3 | 现有产品体验流程 | 关键页面截图、真实代码快照、业务流程图 |
| 4 | 验证案例 | 脱敏的关键实验结果，例如 ABT 结果 |
| 5 | 业务中与体验相关的知识和规则 | 只记录产品特异规则，而不是通识。例如次包、月包、跨月、话费支付等概念 |

备选内容：

| 内容 | 说明 |
| --- | --- |
| 核心参考和竞品 | 带标注的截图，并说明为什么收藏 |
| 数据指标基线情况 | 使用相对脱敏值，例如区间、对比、倍数 |

资料层存储形态：

- 采用文件 + 轻量检索，不上重型基础设施。
- 主目录放快照 snapshot。
- 仅访谈、问卷类数据配置附属 `raw/` 目录，供必要时深挖。

## 5. 原则层：Principles

原则层定位为判断库，回答“怎样才算好”。

原则层分为两块：

### 5.1 通用原则：universal/

通用原则跨业务共享，主要沉淀通用设计与产品判断。

可包含：

- 适合团队的方法论，例如尼尔森可用性原则、峰终定律、格式塔原则、费茨定律等。
- 通用判断框架。
- 通用交互原则。
- 通用体验原则。
- 基础产品设计知识。

### 5.2 业务原则：per-business/

业务原则服务具体业务线，沉淀该业务下“怎样才算好”的判断。

可包含：

- 设计哲学，建议控制在 5000 字以内。
- 组件使用规则，必要时从组件库中拆出。
- 视觉品牌要求。
- 取舍准则，尤其是冲突时的优先级。
- 正反面案例解读。注意这里不是存案例本身，而是解释案例背后的判断。

### 5.3 原则卡片：Principle Card

原则层建议采用原则卡片形式管理。

每条原则一张卡片，固定结构：

```md
P-001 速度感优先（通讯业务）

一句话：所有过渡 ≤ 200ms，加载状态优先于信息完整。

适用场景：#充话费 #流量包 #高频低决策

核心判断：等待感 > 信息完整时，优先消除等待。

正例：充话费首页用骨架屏 + 余额数字先行。

反例：骨架屏等所有数据齐了再渲染。

例外：套餐变更、宽带办理等高决策场景不适用。

相关：与 P-007「信息层级」可能冲突，优先 P-001。
```

数量控制：

- 每个业务建议 15-25 张原则卡片。
- 每个业务建议不超过 8 条取舍准则。
- 如果数量继续膨胀，说明原则可能过度细分，需要合并或上提。

取舍准则特别重要。它是原则层的灵魂，应该由业务决策者亲自起草，不能完全交给 AI 或执行同学代写。

## 6. 应用层：Skills

应用层定位为动作库，回答“具体做什么”。

应用层不是单点 skill 的集合，而是面向设计生产任务组织出的业务整体 skill。它需要调用资料层的事实，并接受原则层的约束。

设计生产工作流可以分为两个阶段。

## 7. 阶段一：洞察与发散

阶段一主要由产品和设计师使用，目标是帮助团队理解需求、调用洞察、判断机会，并形成设计方向。

| 步骤 | Skill 做什么 | 人做什么 |
| --- | --- | --- |
| 1. 输入解析 | 提取关键词，输出“我理解的需求”卡 | 确认理解是否准确 |
| 2. 用户洞察 | 自动圈定客群，调取画像和痛点 | 审阅并补充 |
| 3. 机会判断 | 输出“机会 / 守成 / 风险”判断 | 决策人评审 |
| 4. 发散初稿 | 产出 3-5 个差异化方向，含反向方案 | 评审共识，选择 1 个方向 |
| 5. 共识沉淀 | 把决策记录存入案例库 | 无 |

## 8. 阶段二：交付稿生成

阶段二主要由设计师使用，目标是基于已选方向生成更完整的交付稿，并完成自查和反馈回流。

| 步骤 | Skill 做什么 | 人做什么 |
| --- | --- | --- |
| 1. 高保真生成 | 按选定方向生成全状态稿 + Figma JSON | 审阅结果 |
| 2. 自动自查 | 独立上下文评审：组件、业务规则、设计哲学、无障碍 | 判断修改项 |
| 3. 交付打包 | 整合交付包：稿件、自查、决策记录 | 交付研发 |
| 4. 反馈回流 | 记录设计师的修改原因，反向更新原则层或资料层 | 持续使用和维护 |

## 9. Skill 不做什么

应用层需要有清晰边界。Skill 可以辅助设计生产，但不能替代人的关键判断。

Skill 不做：

- 不替代真实用户访谈。
- 不替代设计师对方向的最终判断。
- 不输出业务决策，只给机会判断。
- 不做 PRD 撰写。
- 不做最终视觉精修。
- 不替代合规审核。

## 10. 当前建设重点

当前阶段优先聚焦设计生产 Harness，尤其是页面生产和 UI 方案生成。

建议优先推进：

1. 梳理资料层一期必做内容，先保证 AI 有事实可查。
2. 建立原则层的 universal/ 通用原则，先补齐 AI 的基础设计判断。
3. 为重点业务建立 per-business/ 业务原则卡片，控制数量，避免过度细分。
4. 设计应用层核心 skill，让它能调用资料层、遵守原则层，并进入真实设计生产链路。
5. 建立反馈回流机制，把设计师修改原因沉淀回资料层或原则层。

## 11. 与 `通用原则.md` 的关系

`通用原则.md` 应属于原则层中的 universal/。

它更像一份 reference，而不是 workflow。它主要沉淀通用设计规则、通用产品知识、基础体验判断和少量正反例，不负责描述具体业务流程，也不规定具体任务的输入输出。

在三层架构中：

- `通用原则.md` 负责给 AI 补齐通用设计判断。
- 业务原则卡片负责补齐具体业务的取舍准则。
- 资料层负责提供组件、用研、案例、业务规则等事实。
- 应用层 skill 负责把这些内容组织进真实设计生产流程。
